# 让 Agent 完成接入配置

[项目主页](../README.zh-CN.md) · **简体中文** · [English](./setup.en.md) · [Agent 顶层入口](../AGENTS.md)

把仓库链接交给 agent，请它配置 Slack 接入。Agent 应先检查已有条件，一次收集缺失前提，再完成支持的配置并验收。用户不需要把 README 的每一步重新翻译成指令。

这是**由 agent 执行的配置流程**，不是跨平台无人值守安装器。Slack 授权、管理员批准、未开放的平台功能和模型凭据可能仍需要用户处理；前提具备后，agent 应在同一次配置任务中继续做到验收。四 agent 协作已有实测，但尚未逐个平台验证从裸仓库链接开始的全新部署。

## 直接发给 Agent

```text
请把 https://github.com/Ares-X/Agents-Slack-Bridge 配置到我的 agent。
先读顶层 AGENTS.md，按 docs/setup.md 执行。
识别目标运行环境，复用已有连接和配置。
先检查你能查到的信息，再一次性告诉我所有缺失信息、权限和必须由我完成的动作。
不要让我在聊天里发送秘密。
这些前提准备好后，继续完成配置、加载，并在约定频道与对端执行有界 Slack 验收。
保留已有工作和权限。提供已配置、已加载、已验收或阻塞的证据，
不要停在计划或 echo 回复阶段。
```

目标、工作区、频道和对端如果已在对话中明确，直接沿用。仅有仓库链接并不能确定要修改哪个账号或部署；缺失的必要选择放到下面的一次性前提清单中。

## 1. 识别目标并检查现状

执行配置的 agent 可以与被接入的 agent 不同：例如 Codex 在服务器上配置 Hermes，应选择 **Hermes** 路线，不能根据自己叫 Codex 就另建一种接入。

| 目标 | 何时选择 | 修改前阅读 |
|---|---|---|
| Muse / 通用本地 agent | 能运行 Python，能调用实际模型或可消费队列的平台 hook | [Muse](../muse/README.md) |
| Grok Bot | 真实 Grok agent 能接收经过认证的唤醒 webhook，并访问部署队列与工具 | [Grok 清单](../grokbot/AGENT.md)、[唤醒约定](../grokbot/AGENT_WAKE.md) |
| Hermes | 目标运行 Hermes，且已有可用模型/provider | [Hermes 清单](../hermes/AGENT.md)、[版本要求](../hermes/README.md) |
| 托管 ChatGPT DOTS | 当前账号具备 Slack 连接及受支持的自动消息事件入口 | [DOTS 清单](../chatgpt-dots/AGENT.md) |
| 其他 | 现有运行环境不符合上述条件 | 检查 Muse 通用 consumer 是否适用；否则先报告缺少哪种适配，不能宣称可以自动完成 |

先检查，不额外启动监听器，也不消费积压消息：

- 目标主机/账号、操作系统、运行时及版本、模型登录、工具和部署权限。本地 bridge 使用 POSIX 能力；不能把 Linux/systemd 步骤套到原生 Windows，也不能假定容器有 systemd。
- 已有 checkout/ref、脏文件、部署路径、私有配置、队列、未完成发送、服务、hook 和托管订阅。记录每个环节的负责人，以及不回滚消息状态的配置恢复方式。
- 已有 Slack App/连接、工作区与频道 ID、公开/私有频道类型、人类所有者 ID、自身 bot 用户 ID、对端用户 ID、频道成员资格、scope 和事件。通过授权工具发现 ID，显示名只用于辅助核对。
- 实际服务账号的网络/代理/CA、可持久写入的状态目录、唤醒真实模型和发回回复的能力。只检查秘密是否存在及可用，不输出值。

仅在首次建立本地 checkout 时执行：

```bash
git clone https://github.com/Ares-X/Agents-Slack-Bridge.git
cd Agents-Slack-Bridge
git rev-parse HEAD
```

已有 checkout 先检查并记录部署 ref，不覆盖克隆或 reset；读取同一 ref 的指南。托管 agent 可以通过工具读取仓库，无需本地 clone。

## 2. 一次性收集缺失前提

**已知值由 agent 自己填写。** 给用户一份简短清单，只列缺失项、用途和具体动作。授权工具能完成的事不要转交给用户。

| 事项 | Agent 应发现或准备 | 仅在必要时请用户完成 |
|---|---|---|
| 目标与常驻运行 | 现有运行时、版本、安装路径、服务负责人、模型能力 | 选择不明确的目标；授权所需安装或服务变更；完成 provider 登录 |
| 协作范围 | 工作区/频道/对端 ID 与现有访问能力 | 选择频道与对端；补充尚未授权的范围，包括有界测试消息 |
| Slack App / 连接 | 复用合适 App；准备所选 manifest 或连接流程 | 批准 Slack 安装/重装或 OAuth；必要时取得管理员批准 |
| 私有凭据 | 检查已有凭据并明确私有存放位置 | 在指定位置或秘密管理界面保存缺失 token/webhook 凭据；只回复“已保存” |
| 频道访问 | 检查成员资格、读取和回复能力 | Agent 无法操作时邀请 bot 或批准访问 |
| 真实 agent 入口 | 找到受支持的模型/hook/webhook/订阅及配置面 | 开启尚不可用的账号功能，或提供实际运行环境的访问权限 |

提问结构示例；发给用户前填入实际内容：

```text
已确认目标为[目标/版本]，将采用[路线]。现已具备：[已有条件]。
还需要你完成：
1. [缺失选择或必须人工完成的动作、具体位置、用途。]
2. [凭据私有存放位置或授权流程；不要发送凭据值。]
完成后我将配置[组件]、加载，并在[约定频道、对端和测试范围]验收。
复用现有[连接/状态]。
```

沿用已有授权，不因为分目录指南写着“确认后”就重复询问。必要答案未收到前不做依赖操作，可以继续独立准备；用户完成清单后继续执行。若后续出现此前无法发现的新阻塞，只询问新增事项并说明变化；“一次收集”不意味着跳过审批或编造平台能力。

### 本地 bridge 与 Hermes 的 Slack App 交接

准备所选路线的 manifest，通过 [Slack App 设置](https://api.slack.com/apps) 创建或更新已授权的 App。安装到目标工作区、启用 Socket Mode，取得 **bot token**（`xoxb-`）及 **app-level token**（`xapp-`，`connections:write`）。需要私信时启用 App Home 消息，并邀请 bot 进入测试频道。值通过私有文件/秘密界面保存。参考 Slack 官方 [manifest 指南](https://docs.slack.dev/app-manifests/configuring-apps-with-app-manifests/)和 [Socket Mode 配置](https://docs.slack.dev/apis/events-api/using-socket-mode/)。

修改已有 App 前先比较当前设置。应用 scope/事件变更并完成 Slack 要求的重装/同意；只修改本地 manifest 不会改变 Slack。Muse 自带 manifest 覆盖公开频道与私信，私有频道事件/历史需要另外核对 scope 与事件变更；Grok manifest 包含私有频道权限和事件；Hermes 从已安装运行时生成 manifest。**托管 DOTS 使用其受支持连接流程，不为它创建这类 token 或安装本地 bridge。**

## 3. 完成所选路线

执行对应目录指南，并遵守以下补充与完成条件。合并私有配置，保留已有值，新凭据不要填入已跟踪的示例。本地 bridge 的 `.env` 加载器需要不带引号的简单 `KEY=value` 行，不是 shell 的 `export` 语法；按该路线实际加载器填写。复用已安装依赖；需要安装的部分纳入约定配置范围。本地命令使用选定虚拟环境，并以所选 agent 目录作为工作目录。

### Muse / 通用本地 agent

1. 按 [Muse 部署指南](../muse/README.md) 配置：仅在 `.env` 不存在时创建；填入 Slack 凭据、已核实身份/对端，以及所需代理和 CA。在选定环境准备 Python 与 `slack_sdk`，不关闭 TLS 验证。
2. 选择**一个实际消费者**。Muse 平台 hook 应绑定真实 hook/调度器、部署队列和目标 agent/side chat；每轮读取最新频道/线程上下文，生成真实回复或静默决定，并调用 `send_durable.py`。仓库不提供平台 hook 及其注册 API，应发现宿主已有能力；没有可用入口时报告缺少消费者能力。
3. 通用本地模型路线需将 `consumer/poll_consumer.py` 的 `generate_reply()` 接到已授权模型，实际使用 `history` 与 session 参数，再配置 consumer 常驻。自带实现只是 echo；不要为同一工作同时启动参考 consumer 和独立 hook。
4. 把协作规则持久写入**实际 hook/模型入口**；使用来源 `channel:ts`、`thread_ts`、显式对端提及，以及 Muse 指南的持久发送/静默/恢复协议。保留已有 uncertain 发送。
5. 加载并管理 listener **及**所选 consumer/hook。只有 socket 已连接、没有自动触发模型回复，属于未完成。

### Grok Bot

1. 按 [Grok 清单](../grokbot/AGENT.md) 复用或创建私有 `.env`，在选定环境安装已声明的 `requirements.txt`，配置已核实 Slack 身份、对端、回复位置、代理和 CA。
2. 绑定真实 agent 唤醒入口。私有 `grokbot/webhook.env` 需要 `WEBHOOK_URL` 和 `WEBHOOK_KEY`；这是经过认证的 **agent 唤醒入口**，不是 Slack Incoming Webhook。权限为 `0600`；在 `.env` 显式设置 `REPLY_MODE=agent_wake`，使所选模式清楚可查。
3. 配置接收端 agent，让其针对**同一部署**的队列和工具执行 [AGENT_WAKE.md](../grokbot/AGENT_WAKE.md) 与[协作规则](../grokbot/PEER_STANDING_RULES.md)。在其执行环境把 `GROK_BRIDGE_DIR` 设为已核实的绝对部署目录。远端接收者需要主机授权访问；webhook 中有路径不等于能读取文件。发送与静默走 `pending_consume_once.py` / `reply_pipeline`，不使用 raw send 后再 ACK。
4. 如果选定解释器位于该位置，在 `grokbot/` 执行 `./venv/bin/python wake_agent.py --check`。它只检查 URL/key 字段能加载，不证明网络可达、认证或模型回合成功；这些通过真实入站消息验收。
5. 管理 `bridge.py` 和 `consumer/poll_consumer.py` 两个组件的常驻。没有可用唤醒配置时正常路线尚未完成，不能切换 `REPLY_MODE=template` 制造成功。若明确选择较慢的备用路线，必须真正调度并唤醒 agent；只写出 `pending.json` 不算。

### Hermes

1. 检查已安装 Hermes 版本、可用 provider/模型登录、现有 gateway 与服务管理器，并复用。缺少安装或模型登录时纳入前提交接，不默默运行安装器或替换工作正常的部署。
2. 创建/更新 App 时，用该运行时的 `hermes slack manifest --agent-view --write` 生成 manifest，已安装 Hermes 也不能漏掉这步。按 [Hermes 清单](../hermes/AGENT.md) 合并 `.env` 与 `config.yaml` 字段，保留其他平台，不产生重复 YAML 键。
3. 分别配置人类授权、bot 消息接收、实际频道/对端范围与回复位置。`allow_bots: mentions` 本身不授权所有对端；核对该版本如何处理携带 user ID 的 bot 帖。默认通知频道不是访问控制白名单。
4. 让**运行中的回合**取得频道/线程历史与协作规则。先查当前版本的原生支持；仓库补丁针对固定上游 `836b5f8…` 并有前置顺序，按[版本说明](../hermes/README.md)检查已有补丁/脏改，兼容补丁先 `git apply --check`，冲突即停，不能强行套到新版。缺少兼容实现时报告需要的适配，不宣称配置已完成。
5. 使用已有 gateway 支持的重载/重启入口，核对实际加载配置/代码，只运行一份 gateway。把历史工具的真实路径登记在已加载的 agent 指引中；正文走原生 adapter 终稿，不另做第二次 raw Slack POST。保留审批机制。

### 托管 ChatGPT DOTS

1. 按 [DOTS 清单](../chatgpt-dots/AGENT.md)检查当前工具和账号设置；Slack 读取、回复和自动事件触发是三个独立能力。
2. 复用已有连接；缺少连接或权限时走受支持 OAuth/同意界面。通过该连接核实频道与作者身份。
3. 原生事件已覆盖目标 bot 消息就复用；否则创建或更新**一条**受支持的新消息订阅，限定约定频道/作者和必要线程事件。把来源核验、最新上下文、原生交接、回复位置、静默完成规则写入实际执行指令，再回读。
4. `config.example.json` 是意图示例，不是导入格式；`reference/` 是离线代码，不控制托管运行时。不编造私有配置文件、不加 cron 轮询，也不往 DOTS 内安装本地 bridge。
5. 当前账号无法订阅目标事件或不能向来源回复时，报告具体能力阻塞。手动读历史不能证明自动触发，不在验收时用它替代事件入口。

### 让配置在当前会话结束后继续生效

本地路线的服务定义需填入正确的绝对解释器/脚本/工作目录，并使用可持久写入的状态目录。Muse 和 Grok 都有名为 `slack-bridge.service` 的模板；同机部署时分配不同服务名，同时修改 Grok consumer 的 bridge 依赖名称。保留预期服务账号及代理/CA 环境。

使用宿主已有监督程序。仓库 unit 是 systemd 示例，不是 macOS/Windows 安装器。核对实际进程归属、重启策略与 consumer 健康，避免 cron/keepalive/systemd 多方重复拉起；不清空队列让健康检查变绿。记录实际状态、日志检查及授权服务重载方式。宿主/容器替换后不能保留配置时，如实列出限制。

托管路线回读已保存连接/订阅与执行指令。每条路线都必须证明实际入口加载了协作规则；只编辑一个运行中的 agent 不会读取的文件不算完成。

## 4. 验收实际效果

在约定测试频道使用新标记，私有记录来源/回复时间戳和链接，以及运行时真实自动触发证据。声称“自动触发”的测试中，不手动唤醒回答者。看似没有回复时先观察核实，再判断能否重试。

| 检查 | 操作 | 通过条件 |
|---|---|---|
| 实际配置 | 回读保存设置，确认正确运行入口/ref | 保存与加载值一致，无重复 listener/consumer/订阅 |
| 真实 agent | 一次已授权人类私信或频道原生提及，问一个非模板小问题 | 真实模型回合，在目标位置恰好一条有用回复 |
| 最新上下文 | 在此前频道消息放一个无害事实，在测试线程补充修正，再原生提及提问且不重复答案 | 使用最新适用事实，回复留在来源线程；历史/工具失败如实报告 |
| 所需线程事件 | 若所选路线配置为支持，在 bot 自己的测试消息下，由已授权人类不加提及地跟帖 | 事件自动进入真实 consumer 并在同一线程回复；顶层提及成功不能代替这项证据 |
| 对端方向 | A→B 再 B→A，分别用新标记，每次探针最多一条回复 | 两个方向都自动触发正确对端一次；逐对记录覆盖 |
| 自然协作 | 向约定参与者给出一个开放任务，例如[共同设计任务](../README.zh-CN.md#试一次共同任务)，不指定发言顺序 | 自行组织、审查、修订并交付共同结果，无人工传话，无持续无意义回环 |
| 完成与健康 | 检查路线可暴露的私有处理/发送状态及运行服务/订阅 | 保留完成证据，失败/不确定状态可见，已有工作仍健康 |

双向探针的一次回复限制只适用于探针，不限制整场讨论。单 agent 配置且暂时没有对端时，完成并报告单端检查，将协作标为 **NOT_EXERCISED**，指出缺少的对端；不要让另一平台阻塞已能完成的本地工作，也不能提前声称完整协作通过。详见[分层验收](./validation.md#分层验收)。

## 5. 交付可用结果

用用户的语言，在其授权的私有目的地交付简短报告：

| 字段 | 必须包含 |
|---|---|
| 目标 | 路线、运行时/版本、仓库 ref、工作区/频道及预期对端 |
| 变更 | 私有配置位置或受支持设置面、脱敏差异、模型/hook 绑定、服务/订阅名称 |
| 状态 | 逐组件区分**已配置、已加载、已验收**；整体为**完成、部分完成或阻塞**并注明原因 |
| 证据 | 来源/回复链接、自动触发证据、上下文/回复位置、条数与实际延迟、测试过的对端方向 |
| 运维 | 实际私有状态/日志/重载指令、恢复位置、持久化限制及保留的 uncertain 项 |
| 剩余项 | 真正缺失的用户动作/能力或未验收项，以及下一步安全操作；不包含秘密 |

用户要求协作接入时，“完成”意味着请求范围内各条路线及上述对端检查通过，而不只是配置写入。缺少必要平台能力时整体结果为部分完成或阻塞。只要求接入一个 agent 时明确报告该较小范围。填写了真实值的部署记录、凭据、队列和私有聊天证据绝不提交到本仓库。
